## 1. 需求分析

### 1.1 原始需求

> 作业1: 分别使用 langgraph 和 openai-agents 实现如下的逻辑：
> - 进程1，接受请求进行情感识别
> - 进程2，得到识别结果后，正向则鼓励，负面则排解
> - 后端进程：接受前端输入，串联进程1和进程2
> - 前端进程：用户输入

### 1.2 需求解读

| 原文表述 | 实际含义 | 设计对应物 |
| --- | --- | --- |
| 进程1 | 情感识别 Agent：对用户输入做情感分类，输出**结构化结果**（正向/负面/中性 + 置信度 + 理由） | 节点 `sentiment` |
| 进程2 | 响应生成 Agent：读取进程1的识别结果，**按情感标签条件路由**——正向→鼓励话术，负面→安慰/疏导话术 | 节点 `respond` + 条件分支 |
| 后端进程 | 编排服务：接收前端请求，按序调用进程1、进程2，聚合结果返回 | FastAPI 服务 + Pipeline 编排层 |
| 前端进程 | 用户交互界面：输入文本、展示识别结果与回复 | Web 页面（HTML/JS） |

### 1.3 功能需求

1. **FR-1 情感识别**：输入一句话，返回结构化情感标签（`positive` / `negative` / `neutral`）+ 置信度 + 简要理由。
2. **FR-2 分流响应**：
   - `positive` → 生成鼓励、祝贺式回复（"趁热打铁"式）；
   - `negative` → 生成共情、安慰、疏导式回复（先接住情绪，再给建议）；
   - `neutral` → 自然接话，避免强行鼓励或安慰。
3. **FR-3 编排串联**：后端把"识别 → 分流 → 响应"串成一条流水线，对外暴露统一的 HTTP 接口。
4. **FR-4 用户交互**：前端提供输入框与对话展示，支持查看"情感标签/理由/回复"的完整结果。
5. **FR-5 双实现等价**：同一套后端接口与前端，可通过配置在 **LangGraph 实现** 与 **openai-agents 实现** 之间切换，两者行为一致（输出结构相同）。

### 1.4 非功能需求

- 模型**可配置**：支持任何 OpenAI 协议兼容模型（OpenAI、DeepSeek、Qwen、GLM 等），通过环境变量切换，不硬编码。
- **可演示、可验证**：提供最小可运行入口和测试用例。
- 前端尽量零构建（无 npm/打包），后端直接托管静态页面。

### 2.2 核心数据流

```
用户输入 text
   │
   ▼
[进程1 情感识别] ──▶ { label, confidence, reason }
   │
   ▼
条件路由 (label)
   ├─ positive ──▶ [进程2-鼓励] ──▶ reply
   ├─ negative ──▶ [进程2-排解] ──▶ reply
   └─ neutral  ──▶ [进程2-接话] ──▶ reply
   │
   ▼
聚合返回 { label, confidence, reason, reply, engine, elapsed_ms }
```

### 2.3 关键设计决策

| # | 决策 | 选择 | 理由 |
| --- | --- | --- | --- |
| D1 | 情感识别输出形式 | **结构化输出**（Pydantic schema），而非自由文本 | 分流逻辑必须依赖可靠的机器可读标签，避免解析自然语言出错 |
| D2 | 进程2 的分流方式 | **编排层显式条件路由**（if/else 选 prompt），而非让模型自己决定 | 与 LangGraph 的 conditional edge 天然对齐，行为确定、可测试；双框架实现可严格等价 |
| D3 | 双实现切换 | 后端编排层统一接口 `run_pipeline(text) -> PipelineResult`，两个实现类实现同一接口，用环境变量选择 | 前端/接口零改动，便于对比两套框架 |
| D4 | 前端方案 | 单个静态 HTML 页面，由 FastAPI 托管，原生 `fetch` 调用 | 零依赖、零构建，满足"用户输入"需求的最短路径 |
| D5 | 模型接入 | 统一走 OpenAI 兼容协议（`OPENAI_BASE_URL` + `OPENAI_API_KEY` + `MODEL_NAME`） | 国内外模型均可适配（DeepSeek/Qwen/GLM/OpenAI），一份代码两套框架复用同一配置 |
| D6 | 会话记忆 | 第一版**无状态**（单轮）；预留 `history` 字段 | 作业核心是编排与分流，多轮记忆作为增强项，不阻塞验收 |

## 3. 核心数据结构

三个进程间传递的唯一契约，两个框架实现共用：

```python
from typing import Literal
from pydantic import BaseModel

SentimentLabel = Literal["positive", "negative", "neutral"]

class SentimentResult(BaseModel):
    """进程1 的输出 = 进程2 的输入"""
    label: SentimentLabel        # 情感标签
    confidence: float            # 0~1
    reason: str                  # 一句话判断依据

class PipelineResult(BaseModel):
    """后端返回给前端的完整结果"""
    user_input: str
    sentiment: SentimentResult   # 进程1 结果
    reply: str                   # 进程2 生成的回复
    branch: str                  # 命中的分支: encourage / comfort / neutral_chat
    engine: str                  # "langgraph" | "openai-agents"
    elapsed_ms: int              # 端到端耗时
```

## 4. 详细设计

### 4.1 后端 API 设计

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 返回前端静态页面 `index.html` |
| GET | `/api/health` | 健康检查，返回当前 engine 与模型名 |
| POST | `/api/chat` | 主接口：接收用户输入，跑完整流水线 |

**POST /api/chat**

请求体：

```json
{ "text": "今天面试通过了，太开心了！" }
```

响应体（`PipelineResult` 序列化）：

```json
{
  "user_input": "今天面试通过了，太开心了！",
  "sentiment": { "label": "positive", "confidence": 0.95, "reason": "用户明确表达通过面试的喜悦" },
  "reply": "太棒了，恭喜你拿到心仪的 offer！你的准备和坚持都有了回报，继续加油！",
  "branch": "encourage",
  "engine": "langgraph",
  "elapsed_ms": 1823
}
```

错误响应：参数缺失 → `422`；模型调用失败 → `502 {"detail": "..."}`。

### 4.2 方案 A：LangGraph 实现

**思路**：用 `StateGraph` 把进程1、进程2 建模为两个节点，用 **conditional edge（条件边）** 实现按情感标签分流——这是本作业与 LangGraph 特性的最佳契合点。

**图结构**：

```
START ──▶ sentiment_node ──(route_by_sentiment)──▶ respond_node ──▶ END
```

**状态定义**（贯穿全图）：

```python
from typing import TypedDict

class GraphState(TypedDict):
    user_input: str
    sentiment: dict        # {label, confidence, reason}
    branch: str            # encourage / comfort / neutral_chat
    reply: str
```

**关键代码骨架**：

```python
from langgraph.graph import StateGraph, START, END
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model=MODEL_NAME, base_url=OPENAI_BASE_URL,
                 api_key=OPENAI_API_KEY, temperature=0.3)

# ---- 进程1：情感识别节点（结构化输出） ----
sentiment_llm = llm.with_structured_output(SentimentResult)

def sentiment_node(state: GraphState) -> dict:
    result = sentiment_llm.invoke([
        ("system", SENTIMENT_SYSTEM_PROMPT),
        ("user", state["user_input"]),
    ])
    return {"sentiment": result.model_dump()}

# ---- 条件路由：进程1 的结果决定进程2 走哪条 prompt ----
def route_by_sentiment(state: GraphState) -> str:
    return {"positive": "encourage",
            "negative": "comfort",
            "neutral":  "neutral_chat"}[state["sentiment"]["label"]]

BRANCH_PROMPTS = {"encourage": ..., "comfort": ..., "neutral_chat": ...}

def respond_node(state: GraphState) -> dict:
    branch = route_by_sentiment(state)
    prompt = BRANCH_PROMPTS[branch]
    reply = llm.invoke([("system", prompt), ("user", state["user_input"])])
    return {"branch": branch, "reply": reply.content}

# ---- 组图 ----
graph = StateGraph(GraphState)
graph.add_node("sentiment", sentiment_node)
graph.add_node("respond", respond_node)
graph.add_edge(START, "sentiment")
graph.add_conditional_edges("sentiment", route_by_sentiment, ["encourage", "comfort", "neutral_chat"])
graph.add_edge("respond", END)
app = graph.compile()

def run_pipeline(text: str) -> PipelineResult:
    state = app.invoke({"user_input": text})
    return PipelineResult(user_input=text, sentiment=state["sentiment"],
                          reply=state["reply"], branch=state["branch"],
                          engine="langgraph", elapsed_ms=...)
```

> 说明：三个分支最终都汇到同一个 `respond_node`，由节点内部按分支选 prompt。若想体现"多节点图"，也可拆成 `encourage_node` / `comfort_node` / `neutral_node` 三个节点，由条件边直接指向——两种写法效果一致，实现时取更清晰者。

### 4.3 方案 B：openai-agents 实现

**思路**：用 OpenAI Agents SDK 的 `Agent` + `Runner`。进程1 用 **`output_type`（结构化输出）** 得到 `SentimentResult`；进程2 按标签动态设定 `instructions` 后再次 `Runner.run`。同样在编排层做显式条件路由，保证与方案 A 行为一致。

**关键代码骨架**：

```python
from openai import AsyncOpenAI
from agents import Agent, Runner, OpenAIChatCompletionsModel, set_tracing_disabled

set_tracing_disabled(True)  # 非 OpenAI 端点无法上传 trace

async def run_pipeline(text: str) -> PipelineResult:
    # 第三方兼容：显式 Chat Completions 模型 + 每次调用独立 client（用完即关）。
    # 注意不要用模块级单例 client——AsyncOpenAI 绑定创建时的事件循环，
    # 多事件循环场景（pytest/TestClient）会触发 "Event loop is closed"。
    async with AsyncOpenAI(base_url=OPENAI_BASE_URL, api_key=OPENAI_API_KEY) as client:
        model = OpenAIChatCompletionsModel(model=MODEL_NAME, openai_client=client)

        # 进程1
        s = await Runner.run(
            Agent(name="SentimentAnalyzer", instructions=SENTIMENT_SYSTEM_PROMPT,
                  output_type=SentimentResult, model=model), text)
        sentiment: SentimentResult = s.final_output

        # 条件路由 + 进程2
        branch = LABEL_TO_BRANCH.get(sentiment.label, "neutral_chat")
        r = await Runner.run(
            Agent(name="Responder", instructions=BRANCH_PROMPTS[branch], model=model), text)

    return PipelineResult(user_input=text, sentiment=sentiment,
                          reply=r.final_output, branch=branch,
                          engine="openai-agents", elapsed_ms=...)
```

**可选增强（体现 SDK 特色，二选一即可）**：
- **Handoff 版进程2**：把 `encourage_agent` / `comfort_agent` 作为 `sentiment_agent` 的 `handoffs`，由模型自主移交。更"agent 化"，但分支选择权交给模型，确定性不如显式路由；作为对比演示项保留。
- **Streaming**：`Runner.run_streamed` 输出增量文本，前端打字机效果（见 §5 增强）。

**两方案等价性对照**：

| 逻辑点 | LangGraph | openai-agents |
| --- | --- | --- |
| 进程1 结构化识别 | `llm.with_structured_output(SentimentResult)` | `Agent(output_type=SentimentResult)` |
| 条件分流 | `add_conditional_edges` | 编排层 `if label == ...`（或 handoff） |
| 进程2 生成 | `respond_node` + 分支 prompt | 动态 `instructions` 的 Responder Agent |
| 串联方式 | 图编排（声明式） | Runner 顺序调用（命令式） |
| 输出契约 | 同一 `PipelineResult` | 同一 `PipelineResult` |

### 4.4 前端设计

单个 `index.html`（原生 HTML/CSS/JS，无构建）：

- **输入区**：多行文本框 + 发送按钮；预置几条示例（一正一负一中性）一键填入，方便演示。
- **结果展示区**：聊天气泡展示回复；下方以"识别卡片"展示 `label`（带图标 🌞/🌧/☁️）、`confidence`、`reason`、`branch`、`engine`、耗时。
- **交互细节**：发送中禁用按钮并显示 loading；`fetch` POST `/api/chat`；错误时在页面顶部提示。

### 4.5 提示词设计（三段共用）

```
SENTIMENT_SYSTEM_PROMPT:
  你是情感识别专家。判断用户输入的整体情感倾向，只输出符合 schema 的 JSON：
  label ∈ {positive, negative, neutral}；confidence 为 0~1 的浮点数；
  reason 用不超过 20 字说明判断依据。不要受用户文字表面礼貌的影响，以真实情绪为准。

ENCOURAGE_PROMPT (positive → 鼓励):
  用户现在情绪很好。请用 2~3 句话真诚地肯定和鼓励用户，指出值得高兴的具体点，
  并顺势激励对方保持状态。语气温暖自然，不说教，不堆砌感叹号。

COMFORT_PROMPT (negative → 排解):
  用户现在情绪低落。请先共情（接住情绪），再温和疏导：帮对方把感受正常化，
  给出 1~2 条可落地的小建议。避免"想开点"这类空话，不说教，不制造二次伤害。

NEUTRAL_PROMPT (neutral → 自然接话):
  用户情绪平稳。请自然地接住话题，简短回应并适度关心，不要强行鼓励或安慰。
```

## 7. 异常处理与边界情况

| 场景 | 处理 |
| --- | --- |
| 输入为空 / 超 500 字 | 422 校验拒绝，前端提示 |
| 模型输出不符合情感 schema | LangGraph `with_structured_output` 与 Agents SDK `output_type` 均会自动重试/校验；仍失败则返回 502 并提示重试 |
| label 不在枚举内（模型幻觉） | 路由函数兜底映射到 `neutral` |
| API Key 缺失/网络错误 | 启动时校验必填项；运行时 502，前端展示错误条 |
| 识别与分流不一致的极端语义（反讽等） | prompt 已要求"以真实情绪为准"；作业范围不做更复杂的多标签/强度分级 |

## 8. 测试方案

1. **单测（tests/test_pipeline.py）**：直接调用 `run_pipeline`，断言
   - 正向样例 → `branch == "encourage"`，`reply` 非空；
   - 负面样例 → `branch == "comfort"`；
   - 中性样例 → `branch == "neutral_chat"`；
   - 两个 engine 各跑一遍同一组样例，结果结构一致。
2. **接口测试**：TestClient 调 `/api/chat`，覆盖参数缺失 422、正常 200。
3. **演示验收**：前端页面依次输入三类样例（如"今天面试通过了！"、"被老板骂了一顿，很委屈"、"明天记得带伞"），确认标签、分支、回复均正确展示。
