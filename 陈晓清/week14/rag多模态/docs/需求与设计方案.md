## 0. 结论先行

1. **前后端分离**：前端 `Streamlit` 独立进程，只通过 HTTP 调后端；后端 `FastAPI` 提供 REST 接口，负责文件、检索、问答；解析由独立 `worker` 进程消费 Kafka 完成。前端不 import 后端代码，不直连 SQLite / Milvus / 模型。
2. **解析统一走 MinerU**（`pipeline` 后端），输出 markdown + 图片，再由 worker 切块、编码、写入 Milvus。不使用 PyMuPDF 解析。
3. **上传与解析解耦**：上传只落盘 + 写库 + 投递 Kafka，接口立即返回；MinerU 在 worker 里慢慢跑。Kafka 不可用时 worker 自动降级为数据库轮询。
4. **复用** Zilliz 云上的 `rag_data_new` 集合（512 维 × 3 路向量），通过 `file_path` 前缀过滤实现数据隔离。
5. **图问**：用户图片和问题一起送 `qwen3.8-max`（已实测支持图片输入），同时用 CLIP 图像向量检索知识库图文作为上下文。
6. 测试用 PDF 已生成：`samples/2025年智能硬件市场分析报告.pdf`（4 页，含 2 张图表）。

## 1. 需求

### 1.1 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-1 | 多文件上传 | 前端一次可选多个 PDF；单文件 ≤ 50MB；保存到 `backend/data/uploads/` |
| FR-2 | 解析状态展示 | `待解析 / 解析中 / 解析完成 / 解析失败`，附带页数、chunk 数、耗时、失败原因 |
| FR-3 | 异步解析 | 上传后投递 Kafka，worker 消费；Kafka 不可用时轮询数据库兜底 |
| FR-4 | 解析与入库 | MinerU 解析 PDF → markdown + 图片 → 切块 → bge / CLIP 编码 → Milvus |
| FR-5 | 文本检索问答 | 问题经 bge 编码，检索 `text_vector`，拼接上下文后调用大模型 |
| FR-6 | 图文混排回答 | 回答中保留并渲染检索到的图片；标注来源文件名与页码 |
| FR-7 | 图问 | 用户上传图片 + 问题，图片随消息送 VLM；同时用 CLIP 检索相似图文 |
| FR-8 | 文件管理 | 列表、删除（同时清理向量）、重新解析、手动触发处理 |
| FR-9 | 运维接口 | 健康检查、统计信息，供前端显示 Kafka / Milvus / LLM / MinerU 状态 |

### 1.2 非功能需求

- **前后端分离**：前端只依赖 `requests` + `streamlit`，后端地址可配置。
- **单机部署**：Windows 10/11，Python 3.12，RTX 4050 Laptop 6GB。
- **接口不被解析阻塞**：上传、状态查询响应时间 < 500ms；解析耗时由 worker 承担。
- **数据可清理**：删除文件时同步删除 SQLite 记录、本地文件和 Milvus 向量。
- **可配置**：所有地址、密钥、路径、阈值走 `.env`，不硬编码。
- **单知识库**：不做多知识库隔离，检索范围限定本项目上传的文档。

### 1.3 明确不做

- 用户体系、登录、权限管理、多租户。
- 评估脚本（页面匹配 / 文件名匹配 / Jaccard）。
- 除 PDF 外的文档格式（docx、txt）。
- 分布式部署、鉴权、限流、任务重试队列。

## 2. 总体架构

```
                    ┌──────────────────────────────┐
                    │   前端（Streamlit :8501）      │
                    │  文件管理 / 解析状态 / 图文问答  │
                    └──────────────┬───────────────┘
                                   │ HTTP (REST + multipart)
                                   ▼
                    ┌──────────────────────────────┐
                    │   后端 API（FastAPI :8000）    │
                    │  文件、状态、检索、问答、图片服务 │
                    └───┬──────────┬───────────┬───┘
                        │          │           │
              ┌─────────▼──┐  ┌────▼─────┐  ┌──▼──────────┐
              │  SQLite    │  │  Kafka   │  │   Zilliz    │
              │ 文件元数据  │  │ rag-parse│  │ rag_data_new│
              └─────────▲──┘  └────┬─────┘  └──▲──────────┘
                        │          │ 消费        │ 写入/检索
                        │     ┌────▼─────────────┴─────┐
                        │     │  worker（独立进程）       │
                        └─────┤  MinerU → 切块 → bge/CLIP │
                              └──────────────────────────┘
                                        │
                              ┌─────────▼─────────┐
                              │ 后端本地磁盘        │
                              │ backend/data/...   │
                              └───────────────────┘
```

**三条主链路**

1. **上传**：前端 → `POST /api/files`（多文件）→ 落盘 + 写 SQLite（`pending`）→ 投递 Kafka → 返回 202。
2. **解析**：worker 消费 Kafka → 状态改 `parsing` → 调 MinerU → 读 markdown/图片 → 切块 → bge/CLIP 编码 → 写 Milvus → 状态改 `done/failed`。
3. **问答**：前端 → `POST /api/chat` → bge（+ CLIP）检索 → 组装上下文 → 调 `qwen3.8-max` → 返回答案 + 来源 + 图片 URL → 前端渲染。

**图片访问**：前端与后端分离后不能直接读后端磁盘，图片统一走 `GET /api/images?path=...`，后端做路径白名单校验后返回文件。

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Streamlit 1.59 | 已安装；三页应用开发快；后续可换 Vue，接口不变 |
| 后端 | FastAPI + Uvicorn | 异步、自动 OpenAPI 文档、multipart 支持好 |
| 数据库 | SQLite（SQLAlchemy 2.x） | 单机足够；API 与 worker 共库，开启 WAL |
| 消息队列 | Kafka（Docker，KRaft 单节点） | 作业要求；Docker 免装 Java/Kafka |
| 文档解析 | MinerU 4.x（`pipeline` 后端） | 作业指定；输出 markdown + 图片；6GB 显存可跑 |
| 文本向量 | `bge-small-zh-v1.5`（512 维） | 参考项目自带，中文效果好 |
| 多模态向量 | `jina-clip-v2`（截断 512 维） | 参考项目自带，图文同一空间 |
| 向量库 | Zilliz Cloud `rag_data_new` | 现成可用（已连通，0 条数据），schema 匹配 |
| 大模型 | `qwen3.8-max`（OpenAI 兼容） | `.env` 已配置；实测支持图片输入 |
| 进程管理 | 三个进程：API / worker / 前端 | 满足前后端与解析解耦 |

## 5. 数据模型

### 5.1 `files` 表

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增 |
| filename | VARCHAR(255) | 原始文件名 |
| stored_path | VARCHAR(1000) | 落盘路径（`backend/data/uploads/<uuid>.pdf`） |
| size_bytes | INTEGER | 文件大小 |
| status | VARCHAR(20) | `pending` / `parsing` / `done` / `failed` |
| status_text | VARCHAR(20) | `待解析` / `解析中` / `解析完成` / `解析失败`（接口直接返回，前端不再映射） |
| page_count | INTEGER | PDF 页数（MinerU 输出统计） |
| chunk_count | INTEGER | 入库 chunk 数 |
| parse_seconds | REAL | 解析 + 入库耗时 |
| error | TEXT | 失败原因（截断 2000 字符） |
| kafka_queued | BOOLEAN | 是否成功投递 Kafka |
| created_at / updated_at | DATETIME | 时间戳 |
| started_at / finished_at | DATETIME | 解析起止 |

索引：`status`、`created_at`。

### 5.2 Milvus `rag_data_new`（复用，不改 schema）

| 字段 | 类型 | 本项目用法 |
|---|---|---|
| id | INT64 auto | 自动主键 |
| text_vector | FLOAT_VECTOR(512) | bge 文本向量 |
| clip_text_vector | FLOAT_VECTOR(512) | CLIP 文本向量（预留，融合检索用） |
| clip_image_vector | FLOAT_VECTOR(512) | CLIP 图像向量；chunk 无图时零向量 |
| db_id | INT64 | 对应 `files.id` |
| text | VARCHAR(1024) | chunk 文本，**以 `[第N页]` 开头** |
| file_name | VARCHAR(256) | 原始文件名 |
| file_path | VARCHAR(512) | 原始 PDF 绝对路径（隔离与展示用） |

> **页号方案**：集合没有 page 字段，因此把页号写进 `text` 前缀，例如 `[第3页] 图中左侧设备为...`；接口返回来源时用正则解析。
>
> **隔离方案**：检索时加过滤 `file_path like "<DATA_DIR 绝对路径>%"`。若项目目录迁移，旧向量需重新解析。

## 6. 状态机

```
            上传成功
               │
               ▼
          ┌─────────┐   worker 开始   ┌─────────┐   入库成功   ┌────────┐
          │ pending │ ─────────────▶ │ parsing │ ───────────▶ │  done  │
          │ 待解析   │                │ 解析中   │              │ 解析完成│
          └────┬────┘                └────┬────┘              └────────┘
               │                          │ 异常
               │ 手动重试                  ▼
               │                     ┌─────────┐
               └────────────────────▶│ failed  │
                                     │ 解析失败 │
                                     └────┬────┘
                                          │ 重新解析（先删旧向量）
                                          ▼
                                      pending
```

- 允许 `failed → pending`（重新解析）、`done → pending`（重新解析，先删 `db_id` 旧向量）。
- `parsing` 超过 30 分钟视为僵死，允许手动重置为 `pending`。

## 8. Kafka 设计

| 项 | 值 |
|---|---|
| Topic | `rag-parse` |
| 分区 | 3 |
| 消息 key | `file_id`（保证同文件顺序） |
| 消息体 | `{"file_id":1,"file_name":"报告.pdf","stored_path":"...","requested_at":"..."}` |
| 消费组 | `rag-parse-worker` |
| 提交方式 | 手动提交，处理成功后 commit |
| 关键参数 | `max_poll_interval_ms=1800000`、`session_timeout_ms=60000`、`auto_offset_reset=earliest` |

**worker 三种模式**

- `auto`（默认）：先尝试连 Kafka，成功则消费；失败则切轮询。
- `kafka`：只消费 Kafka，连不上直接退出。
- `poll`：每 5 秒扫描 `status='pending'` 的记录并处理。

> 长解析任务（MinerU 1 分钟以上）会超过默认 5 分钟的 `max_poll_interval`，因此调大到 30 分钟，并关闭自动提交。

**Kafka 容器**（`deploy/docker-compose.yml`）

```yaml
services:
  kafka:
    image: apache/kafka:3.9.1
    container_name: rag-kafka
    ports: ["9092:9092"]
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093
```

## 9. 解析与入库流程

```
pending
  └─▶ 状态置 parsing，记录 started_at
        └─▶ MinerU:
              mineru -p <pdf> -o backend/data/processed/<file_id> -b pipeline -l ch
              （具体参数以安装后 `mineru --help` 为准）
            输出：content.md、images/、*_content_list.json、*_middle.json
        └─▶ 读 content.md，按块聚合切分（目标 300 字符，硬上限 1000 字节）
        └─▶ 从 content_list.json 取 page_idx，生成 `[第N页]` 前缀
        └─▶ 图片引用改为绝对路径
        └─▶ 每个 chunk 编码三路向量：
              text_vector       = bge(chunk 纯文本)
              clip_text_vector  = clip(chunk 纯文本)
              clip_image_vector = clip(第一张图) 或 零向量
        └─▶ 先删 db_id 旧向量（重解析场景），批量 insert（16 条/批）
        └─▶ flush，写 chunk_count / page_count / parse_seconds
        └─▶ 状态 done（失败则 failed + error）
```

**切块规则**

- 过滤空行、`# References` 之后的参考文献行。
- 标题、段落、表格、图片行都作为独立块参与聚合；图片行单独成块，保证图文对应。
- 单行超过 300 字符时按句子切分。
- `text` 总字节数超过 1000 时按 UTF-8 安全截断。
- 同一页的块在文本里保留页号前缀，便于回答标注来源。

**MinerU 输出定位**

- 优先使用 `content_list.json`（含 `page_idx`、`type`、`img_path`）。
- 找不到时退回 `content.md` + `middle.json` 的 `page_idx`。
- 都找不到页号时记 0，不阻断入库。

## 10. 检索与问答

### 10.1 检索

| 场景 | 查询向量 | 检索字段 | 数量 |
|---|---|---|---|
| 纯文本问题 | bge(question) | `text_vector` | 8 |
| 带图片问题 | 上述文本检索 + clip(image) | `text_vector` + `clip_image_vector` | 8 + 4 |

- 过滤条件：`file_path like "<DATA_DIR 绝对路径>%"`（仅本项目数据）。
- 距离为 L2，越小越相似。
- 融合去重：按 `(db_id, text)` 取最高分，最终保留 `top_k=6`。
- 每条结果解析 `[第N页]` 得到页码，并提取 chunk 内的图片引用。

### 10.2 Prompt

```
你是严谨的文档问答助手。只依据【资料】回答【问题】。

【问题】...
【资料】
[第2页｜来源：报告.pdf]
...
[第3页｜来源：报告.pdf]
...

要求：
1. 只使用资料信息，没有就说“资料中未提及”，禁止编造。
2. 答案末尾用「来源：文件名 第N页」标注依据。
3. 资料中的图片用 ![说明](原始路径) 原样保留在相关段落旁，不要改写路径。
4. 如果用户提供了图片，结合图片内容回答，并明确区分“图片中”和“资料中”。
5. 简洁、分点，不要复述资料原文。
```

### 10.3 图问

- 用户图片经后端压缩（最长边 1024px、JPEG 85）后转 base64 data URL。
- 消息结构：`system` + `user[text(prompt), image_url(用户图), image_url(检索图1..2)]`。
- 是否附带检索图片由 `CHAT_INCLUDE_RETRIEVED_IMAGES` 控制（默认 true，最多 2 张）。
- 模型返回的 markdown 图片路径由后端替换为 `/api/images?path=...`，前端直接渲染。
- 图片 token 成本较高，`MAX_INLINE_IMAGES` 默认 2。

## 11. 前端页面

### 11.1 `app.py`

- `st.set_page_config`，`st.navigation` 三个页面。
- 顶部状态条：后端 / Kafka / Milvus / LLM 健康状态（调 `/api/health`，30 秒缓存）。
- 后端不可达时显示启动命令，不抛异常。

### 11.2 文件管理

- `st.file_uploader(accept_multiple_files=True, type=["pdf"])`。
- 上传后显示每个文件的结果：`已入队` / `入队失败（将由轮询处理）` / `被拒绝`。
- 文件表格：文件名、大小、状态、页数、chunk 数、上传时间。
- 操作：删除、重新解析、立即处理（兜底）。
- 删除前二次确认（`st.popover` 或 checkbox）。

### 11.3 解析状态

- 顶部指标卡：待解析 / 解析中 / 解析完成 / 失败。
- 自动刷新：`st.fragment(run_every=3)` 开关；关闭时显示手动刷新按钮。
- 列表按更新时间倒序；失败项可展开看 `error`，并提供“重新解析”。
- 解析中显示已耗时。

### 11.4 图文问答

- 聊天历史存 `st.session_state`，刷新页面不丢（同一会话）。
- 侧边栏：附加图片（`st.file_uploader`）、清除图片、清空对话、`top_k` 滑块。
- 发送：question + 可选图片 → `/api/chat`。
- 渲染：`st.markdown` 文本 + `st.image(API_BASE + url)` 图片。
- 来源：`st.expander` 展示文件名、页码、相似度、片段前 120 字。
- 流式输出暂不做（`stream=False`），后续可加 SSE。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| MinerU 4.2.1 与现有 torch 2.6 / transformers 4.56 版本冲突 | 装不上或跑不起来 | 先 `pip install --dry-run` 检查；冲突则给 backend 建独立 venv；锁定版本 |
| MinerU 模型下载约 2GB、单份 PDF 约 1 分钟 | 首次启动慢 | 后台下载；Kafka 异步；README 写清前置步骤 |
| 显存 6GB（当前空闲约 4.3GB） | 解析 OOM | 单并发；`pipeline` 后端；解析前提示关闭其他占显存程序 |
| Docker Desktop 未启动 | Kafka 不可用 | 提供 `docker compose up -d`；worker 自动降级轮询；前端状态条提示 |
| 共享集合被他人写入 | 检索到无关数据 | `file_path` 前缀过滤；删除只按 `db_id` + 自己的路径 |
| 长解析触发消费者 rebalance | 重复消费或提交失败 | 手动提交 + `max_poll_interval_ms=30min` + 幂等（先删后插） |
| `text` 字段 1024 字节 | 写入失败 | 1000 字节安全截断 |
| 中文路径 / 空格 | MinerU 子进程失败 | `subprocess` 传列表、不用 `shell=True`、显式 `cwd` |
| Streamlit 无法显示本地图片 | 图文混排失效 | 统一走 `/api/images` HTTP 地址 |
