# 对比总结：LangGraph vs OpenAI-Agents 实现同一业务

两套实现完成**相同的业务逻辑**（记忆检索 → 情感识别 → 分支回应 → 记忆回写），
但在抽象模型与编程范式上有本质差异。下表按维度逐一对比。

## 一、核心差异速览

| 维度 | LangGraph | OpenAI-Agents |
|------|-----------|---------------|
| 抽象模型 | **图（Graph）**：节点 + 边 | **多 Agent + 显式编排** |
| 处理单元 | 节点函数 `retrieve_memory / classify / ...` | `Agent` 对象 `sentiment_agent / cheer_agent / ...` |
| 状态 | 显式 `TypedDict` 的 `State` 在节点间流转 | `RunResult` 按次返回，无共享图状态 |
| 分支/路由 | `add_conditional_edges` 条件边（框架内置） | 手动字典分派（代码自己写） |
| 结构化输出 | `with_structured_output(Schema, method="json_mode")` | `Agent(output_type=Schema)` |
| 调用方式 | `graph.invoke(...)`（同步，可流式） | `await Runner.run(...)`（异步） |
| 多轮记忆 | `State` 载入 + 节点回写（本实现走共享 storage） | 主流程显式读写 storage |

## 二、逐维度展开

### 1. 抽象模型：图 vs 多 Agent

**LangGraph** 把流程显式建模成一张**有向图**：

```python
builder = StateGraph(State)
builder.add_node("classify", classify)
builder.add_node("cheer", cheer)      # 三个回应节点
builder.add_conditional_edges("classify", _route, {...})
graph = builder.compile()
graph.invoke({"text": ...})
```

控制流（先识别、再根据结果走哪条支路）由**图结构本身**表达，一眼看出拓扑。

**OpenAI-Agents** 把每个步骤建模成一个 **Agent**，控制流靠**宿主代码**（我们的
`run_pipeline`）串起来：

```python
result1 = await Runner.run(classifier, text)
sentiment = result1.final_output_as(SentimentResult).sentiment
reply_agent = _REPLY_AGENTS[sentiment]
result2 = await Runner.run(reply_agent, ...)
```

「先跑谁、再跑谁、怎么分支」全部写在函数体里，拓扑不显式，但更直白。

### 2. 状态与数据流转

- **LangGraph**：`State` 是贯穿全程的共享字典。每个节点只返回需要更新的字段，
  框架负责合并。节点之间天然共享 `text / sentiment / reply`。
- **OpenAI-Agents**：每次 `Runner.run` 是独立调用，返回独立的 `RunResult`。两次
  Run 之间的数据靠 Python 变量显式传递（这里就是 `sentiment` 变量）。

结论：LangGraph 适合「多节点共享状态」的复杂流程；OpenAI-Agents 适合「Agent 之间
松耦合、靠返回值衔接」的场景。

### 3. 分支/路由的写法差异（最能体现两者风格）

题目要求「正向鼓励、负面排解、中性回应」，这是一个三分支路由：

- **LangGraph** 用**条件边**，把路由声明为图的一部分：

```python
builder.add_conditional_edges(
    "classify",
    _route,                                  # 返回 "positive"/"negative"/"neutral"
    {"positive": "cheer", "negative": "comfort", "neutral": "neutral"},
)
```

- **OpenAI-Agents** 用**字典分派**，路由写在业务代码里：

```python
_REPLY_AGENTS = {"positive": cheer_agent, "negative": comfort_agent, "neutral": neutral_agent}
reply_agent = _REPLY_AGENTS[sentiment]
```

一个「声明式」、一个「命令式」，是理解两框架心智模型的关键切入点。

### 4. 结构化输出对比（含 DeepSeek 实战坑）

两者都基于 Pydantic，但挂载位置不同：

| | LangGraph | OpenAI-Agents |
|---|---|---|
| 写法 | `llm.with_structured_output(SentimentResult, method="json_mode")` | `Agent(..., output_type=SentimentResult)` |
| 作用对象 | 一个 LLM 调用 | 一个 Agent（整个 Agent 的最终输出被约束） |
| 取结果 | `parsed.sentiment` | `result.final_output_as(SentimentResult).sentiment` |
| 底层机制 | `response_format=json_object` | tool calling（`tool_choice=auto`） |

**实战坑（DeepSeek 思考模型）**：`response_format=json_schema` 与强制
`tool_choice` 均被 400 拒绝。因此 LangGraph 侧必须显式 `method="json_mode"`；
Agents 侧 `output_type` 可用（auto 路径），但仍需文本 JSON 提取兜底——两框架
的降级链完全一致：**原生结构化 → `extract_json_dict` 文本提取 → 关键词兜底**。

### 5. 调用范式：同步图 vs 异步 Agent

- LangGraph 的 `graph.invoke` 是同步（也支持 `astream` 异步流式）。
- OpenAI-Agents 的 `Runner.run` 是 `async`，需在事件循环里 `await`，我们的
  FastAPI 接口也因此定义为 `async def chat(...)`。

### 6. 多轮记忆实现对比（本作业 v2 的核心增量）

两框架刻意**共用同一套 SQLite 存储层**（storage/repository），对比才公平：

| | LangGraph（langgraph_flow.py） | OpenAI-Agents（agents_flow.py） |
|---|---|---|
| 记忆检索 | `retrieve_memory` 节点读库并渲染进 `State` | `run_pipeline` 开头读库，Python 变量传递 |
| 记忆注入 | 节点函数从 `State` 取 `history / memory` 拼 prompt | 主流程把变量拼进 Runner 输入 |
| 记忆回写 | `store_memory` 节点（图内闭环） | 主流程尾部（编排内闭环） |
| 框架原生方案 | checkpointer（本项目未用，存储层统一代替） | `to_input_list()` 拼历史（本项目未用，同理） |

**共同点**：提示词模板（prompts/*.j2）两框架 1:1 复用，`render()` 出完全相同的
prompt 文本——保证模型行为差异只来自框架调用机制本身。

LangGraph 原生的 checkpointer 是为「图状态断点续跑」设计的；OpenAI-Agents 的
`to_input_list()` 是为「消息列表复用」设计的。本作业的跨会话持久记忆两者都做不到
开箱即用，因此统一收敛到自建 storage 层——这也是应用级工程里常见的选择：
**框架管编排，存储管事实**。

## 三、适用场景建议

| 场景 | 推荐 |
|------|------|
| 明确的多步流水线、需要可视化拓扑、复杂条件分支、状态共享 | **LangGraph** |
| 多个相对独立的 Agent 各司其职、强调单个 Agent 的指令/工具/守卫 | **OpenAI-Agents** |
| 本作业这种「简单两段 + 三分支」 | 两者皆可，正好用来对照学习 |

## 四、一句话总结

- **LangGraph 用「图」描述流程**：把节点和边作为一等公民，控制流是声明式的。
- **OpenAI-Agents 用「Agent + Runner」描述流程**：把智能体作为一等公民，控制流
  由宿主代码命令式编排。

同一个业务，两套心智模型；理解了这一点，就掌握了第 15 周「编排 Agent 工作流」
的核心。
