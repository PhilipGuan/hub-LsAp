# FoodLens 设计文档

## 1. 背景与目标

FoodLens 是一个 Web 应用：用户拍摄一餐（多道菜同框）或包装食品的营养标签，系统识别菜品/读取标签，估算热量与三大营养素。

**与 UrbanUnbox 的关系（关键教训）**：UrbanUnbox 验证了「VLM 擅长感知与判别，不擅长开放集实体识别；事实与数值应走检索」。FoodLens 从第一天就采用该结论——**VLM 只负责感知，热量数值一律来自营养数据库 + 确定性计算**，不由模型"背"。

## 2. 需求（冻结）

| 维度 | 结论 |
| --- | --- |
| 核心场景 | 拍一餐（多菜品，第一优先）；兼顾包装食品营养标签 OCR |
| 输出 | 总热量 + 每道菜分项 + 三大营养素（蛋白 / 脂肪 / 碳水） |
| 产品形态 | Web 应用（手机浏览器拍照 / 上传） |
| 准确度 | 评估集上热量误差 ±15% 内 |
| 食物范围 | 中西兼顾（双语营养库） |
| 交互 | 允许轻量修正（增删菜品、调克数、实时重算） |
| 双语 | UI 文案与 LLM 输出支持中英自由切换 |

## 3. 架构分层

```text
[手机浏览器]
   │  拍照/上传
   ▼
React 前端  ── 菜品卡片(可增删)、克数滑杆、双语切换、实时重算
   │  HTTP
   ▼
FastAPI 后端
   ├─ 感知层 (VLM)      : 识别每道菜(中英名) + 粗分量 + 营养标签OCR
   ├─ 归一 / 检索层      : 菜名(中英/别名) → 营养库匹配
   ├─ 计算层            : 库中「每100g营养」× 估算克数 → 分项/总量/三大营养素
   └─ 会话/编排层        : 支持轻度修正（增删菜品、调量、重算）
   │
   ▼
营养数据库 (本地 JSON 索引 + 检索)
```

**两条铁律：**

1. **VLM 只做感知**（菜品识别、标签 OCR、粗分量），**数值一律来自营养库 + 计算**。
2. 每条结果**可解释**（标明来源库条目）、**可修正**（用户改量即重算，不重新调用 VLM）。

## 4. 营养数据层

食物记录 schema：

```json
{
  "id": "hongshaorou",
  "name": {"zh": "红烧肉", "en": "Braised Pork Belly"},
  "aliases": ["红烧五花肉", "Braised Pork"],
  "category": "dish",
  "per_100g": {"kcal": 472, "protein": 12.0, "fat": 45.0, "carb": 3.0},
  "standard_servings": [
    {"label": {"zh": "一份(约150g)", "en": "1 serving (~150g)"}, "grams": 150}
  ],
  "source": "china_fct"
}
```

数据来源（自建 + 开源混合）：

- **自建中餐菜品库**：常见家常菜 / 餐馆菜 / 外卖菜，逐步扩充。
- **USDA FoodData Central**：西餐主食、食材。
- **Open Food Facts**：包装食品。

加载与检索：启动时加载为本地索引；匹配顺序为 **精确名 → 别名 → 模糊匹配**；命中返回 `id`，未命中标记为"未收录"。

## 5. 识别与计算管线

```text
1. 上传图片
2. VLM 感知 → [{菜名(中英), 克数估计, 置信度}]   或  {标签OCR数值}
3. 归一      → 逐条匹配营养库(精确→别名→模糊)，命中留 id，未命中标记
4. 计算      → Σ(每100g营养 × 克数/100) → 每道菜分项 + 总热量 + 三大营养素
5. 返回      → 前端渲染卡片
6. 用户修正  → 增删菜品/改克数 → 后端重算(不重新调用VLM)
```

## 6. 分量估计与护栏

初始分量由 **VLM 直接估克数**（用户选择）。

**护栏（抑制离谱误差）**：当 VLM 给出的克数明显偏离库中该菜的标准份范围时，向其合理区间收敛，并在结果中标注"已校准"。此护栏不改变"直接估克数"的主路径，仅拦截异常值。

## 7. 前端交互

- **拍摄 / 上传** → 结果页以**菜品卡片**呈现：双语名称、克数滑杆、每道菜热量 + 三大营养素。
- **轻量修正**：增删菜品、拖动克数 → 防抖后调"重算接口"（不重新调用 VLM）。
- **未收录菜品**：标"未收录"；可选展示 VLM **区间估算**并明确标注"估算"，不伪装成实测。
- **标签 OCR 模式**：直接展示解析出的营养成分表数值。
- **中英切换**：接口**同时返回中英双语字段**，前端本地切换、无需重新请求。

## 8. 错误处理与降级

| 情况 | 处理 |
| --- | --- |
| VLM 超时 / 失败 | 提示重试，保留上次结果 |
| 菜名未收录 | 标"未收录"，不编造；可选区间估算并明确标注 |
| 一菜名匹配多条 | 让用户在候选中选择 |
| 标签 OCR 失败 | 提示重拍（对准营养成分表） |
| 克数异常 | 收敛到库中标准份范围并标注"已校准" |

## 9. 测试与评估

- **单元测试**：营养计算、库加载 / 匹配、归一逻辑。
- **评估集**：一组标注图片（图 → 期望菜品 + 克数 + 热量），计算**菜名命中率**与**热量 MAE**。
- **回归**：改库后一键重跑。
- **验收目标**：评估集上热量误差落在 ±15% 内。

```text

├── backend/
│   ├── app/
│   │   ├── main.py / schemas.py / config.py / orchestrator.py
│   │   ├── nutrition/           # 数据层：加载/索引/检索 + data/*.json

│   └── tests/

└── README.md
```

技术选型（沿用已验证栈）：

- 后端：Python 3.11+、FastAPI、uv 管理依赖。
- 视觉：OpenAI 兼容 / Qwen 多模态（`qwen3-vl-plus`），可配置 Provider。
- 前端：React + TypeScript + Vite。

## 11. 范围边界（本期不做）

- 不做用户账户与云端历史同步。
- 不做移动原生 App。
- 不做条形码扫描（仅营养标签 OCR）。
- 不做多图 / 视频输入。
- 不做社区与分享功能。

## 12. 风险与开放问题

- **±15% 的现实性**：单图估克数本身有不确定性。"直接估克数 + 护栏 + 用户修正"是当前设定；若评估集不达标，需回退到"份数映射标准份"策略。此风险在评估阶段验证。
- **中餐部分菜品营养差异大**（同一道菜做法差异可达数倍），自建库以"常见做法均值"入库，并在前端标注估算性质。
