# 设计取舍（DESIGN）

这份文档只回答一类问题：**为什么长这样。** 逐文件搬迁记录在 [MIGRATION.md](MIGRATION.md)。

---

## 1. 核心主张：Structure vs Prompt（护栏做进代码结构，而不是提示词）

整个项目的地基是一条价值判断：**能确定性判定的，绝不交给模型的自觉。**

| | Prompt 约束（概率性） | 本项目 Structure（确定性） |
|---|---|---|
| 只读 | 提示词里写「只准写 SELECT」 | `is_readonly()`：去掉注释与字符串字面量后，要求首词为 `SELECT`/`WITH`、拒绝多语句、拒绝写关键字 |
| 失败时 | 模型可能不听 | 返回 `(False, 原因)` → 流水线**直接放弃**，根本不调用 `execute_sql` |
| 结果 | 「希望」不写坏语句 | 写操作**在到达数据库之前就被代码挡掉**，与模型意愿无关 |

推论：**范围闸门**（`scope_check`）也是结构性的——守门人只输出 JSON，且若它声称 `in` 却落不到
任何真实表，**强制降级为 `ambiguous`**，避免把越界问题硬编成 SQL。

## 2. 边界：「不是所有东西都该 LangChain 化」

引入框架不等于「全部重写」。本项目划了一条清晰的线：

**该 LangChain 化的（换框架有真实收益）**

| 部件 | 换成 | 收益 |
|---|---|---|
| 模型接入 | `ChatOpenAI` | provider 无关，不再伪造 `os.environ` |
| 重试 | `with_retry` | 框架内建，删掉手写循环 |
| 提示词 | `ChatPromptTemplate` | 变量注入与消息类型受类型系统约束 |
| 结构化输出 | `with_structured_output(Pydantic)` | 从「`json.loads` + 约定」变成「校验过的对象」 |
| 编排 | LangGraph `StateGraph` | 拓扑可画、可核对，未来可接 checkpointer 断点续跑 |
| 自主路径 | `create_agent` + `@tool` | 标准工具协议，工具描述由签名 + docstring 自动生成 |

**刻意不 LangChain 化的（框架只会添乱）**

| 部件 | 为什么不换 |
|---|---|
| `is_readonly()` 只读守卫 | 这是**安全边界**，必须是一段短、可读、可单测、无依赖的纯 Python。包成 `Runnable` 只会让它更难审计 |
| `DBParser` 表反射 | 纯数据访问，与 LLM 无关；SQLAlchemy 已经是最合适的抽象层 |
| `normalize_rows` / `row_equal` 等确定性判分 | 评测的**可信度**来自确定性；交给框架/模型反而引入不确定性 |
| `find_up` / `load_env` / `redact` | 配置与脱敏，越简单越安全 |

> 判据很简单：**这段逻辑是不是「让模型说话」？** 是 → 走向 LangChain；不是 → 保持纯 Python。

## 3. 为什么 `workflow/` 与 `agents/` 两条路都要留

这不是「两套实现」的冗余，而是**同一内核的两种驱动方式**：

| | `workflow/graph.py` | `agents/sql_agent.py` |
|---|---|---|
| 谁来编排 | 写在 Python 里（LangGraph 显式图） | 交给模型（`create_agent`） |
| 每步调用 | 固定 7 阶段，各一次 LLM | 模型自主决定调用哪个工具、几次 |
| 可预测性 | 高（每步可断言、可单测） | 低（行为由模型决定） |
| 适用 | 流程稳定、要审计、要复现 | 探索性强、工具组合开放 |

**关键事实**：LangChain v1 的 `create_agent` **内部就是用 LangGraph 实现的**——
所以它们不是竞品，而是「用不用显式图」的区别。

两者**共用同一套内核**：都经 [tools.py](sqlagent/tools.py) 拿 schema、跑 SQL。
`tools.py` 的文档里写明「**这是两条路的唯一入口**」——换库、改守卫、加审计都只改一处。

## 4. 评测装置的设计（为什么是 L0–L5）

### 4.1 为什么要逐层

一次问答的错误可能注入在 5 个跳跃点：

```
问题 ─①→ 选表 ─②→ 生成 SQL ─③→ 校验 ─④→ 执行 ─⑤→ 汇总回答
```

只看终点值有两个问题：**无法定位**；且会放过「结论对、过程错」（选错表却恰好数值撞对）。
逐层裁判把失败**钉到具体一跳**，并给出可读理由。

### 4.2 两条第一性原理

1. **可判定 vs 需判断**：数值是否相等、SQL 能否执行、有无写操作、答案数字能否溯源——
   这些用**代码断言**即可；只有「这条 SQL 是否忠实表达了问题」才交 LLM 裁判。
2. **LLM 裁判必须带参照物**：喂「问题 + 待审 SQL + 权威 SQL」，把「你觉得对吗」变成
   「对照批改（rubric + reference）」，否则退化成两个模型对喷。

### 4.3 两处「确定性 → LLM」升级（只在代码判不死时才动 LLM）

- **L4**：结果集「严格相等」只是**充分不必要条件**——Agent 可能把姓名拆成两列，语义没错但形状不同。
  故确定性比较判不一致时，升级 LLM 做「口径是否一致」复核。
- **L1**：选表覆盖了必需表但**多选了表**时，交 LLM 判多余表是否改变口径。

> 这样既避免「用 LLM 做本来能确定性判定的事」（贵且不稳），又避免「用确定性判据卡死语义等价的正确答案」。

### 4.4 验证集为什么要冻结

`ref_rows` 由手写 `ref_sql` 经**双引擎（SQLAlchemy + 原生 `sqlite3`）交叉验证**后固化
（`freeze_golden()`），评测**只读、绝不重算**。理由：

- **可复现**：同一份答案，谁跑都一样；
- **答案独立于答题模型**：避免「用被测模型生成标准答案」的自证偏差。

### 4.5 诚实暴露 `None`

裁判返回 `None`（如 JSON 解析失败）表示「**未给出结论**」，不计入通过性，
但会在明细里**显式暴露**——宁可暴露「没判」，也不假装「判过了」。

### 4.6 信号 vs 判决：L2 与 L4 是两种信息，不是同一件事

同一个「对不对」被拆成了两种严格不同的判据：

| | L2 | L4 |
|---|---|---|
| 看什么 | **SQL 怎么写**（写法等价） | **跑出来是什么**（结果等价） |
| 比较对象 | 过滤 / 连接 / 聚合 / 排序 / 取值列 | 行集合与每行取值 |
| 忽略 | 别名、列顺序等表层差异 | 列拆分、行序、数值格式 |
| 角色 | **审查信号**：写法变了，值得看一眼 | **判决**：数据到底对不对 |

一次真实的实验（`STRUCTURE_PROBES`，5 道复杂结构题）说明这个分工不是冗余：

- 5 题 **L4 结果等价 5/5 通过**，而 **L2 亮灯 3/5**——理由是「缺 `ORDER BY`」「少了 `ROUND`」
  这类**化妆性差异**，以及 `RANK` vs `ROW_NUMBER` 这类**可辩护的真差异**。
- 若把 L2 当硬门槛，就会把「结论完全正确」的题判成错——**这是口径设定问题，不是 bug**。
- LLM 裁判还带 **run-to-run 抖动**（同代码连跑两次，L2 亮灯数在 3/5 与 4/5 间摆动），
  所以**单次结论不能当硬门**。

结论：L2 与 L4 分别交付「过程信号」与「结果判决」两种信息，让使用者能区分
「**写法不同但结果对**」与「**结果本身就错**」。因此这组探针**不并入验证集的通过性统计**，
只作为**探针**常驻监视 L2 的稳健性——**要当硬门槛，得先决定 L2 的口径**。

## 5. 一处「好失败」（G7）

`每位客服各自负责多少位客户？`：

- Agent 用 `LEFT JOIN` + `WHERE e.Title = 'Sales Support Agent'`；权威 `ref_sql` 用 `INNER JOIN`、不按 Title 过滤。
- **L2 生成层判 FAIL**（连接关系 / 过滤条件不同），**L4 结果层判 PASS**（21/20/18 完全一致）。

这恰恰是逐层裁判的价值：**定位到具体一跳并给出可读理由**，而不是笼统报个「错」。
`L2 口径分歧 ≠ 结果错`——最终谁对仍需人工判定。装置不负责替你下结论，只负责把分歧点亮。

## 6. 一次真实的 bug：`with_retry()` 会丢模型级能力

真实端到端冒烟时炸出：`AttributeError: 'RunnableRetry' object has no attribute 'with_structured_output'`。

原因：`model.with_retry()` 返回的是 `RunnableRetry`——一个**链路上的 Runnable**，
不再是「模型」，因此**没有** `with_structured_output()` / `bind_tools()` 这些模型级能力。

修法（见 [llm.py](sqlagent/llm.py)）：

```python
# 错误：先套重试，再想要结构化 → 已经晚了
# model.with_retry(...).with_structured_output(schema)

# 正确：先用原生模型拿到能力，再给结果套重试
build_raw_model(attempts=0) \
    .with_structured_output(schema, method="json_mode") \
    .with_retry(stop_after_attempt=3)
```

**教训**：离线单测用的是假模型，测不出这类「框架类型」问题；**必须做真实端到端冒烟**。
这也是为什么本项目坚持「三关验证」：`pytest` + 真实 DeepSeek 两路冒烟 + 12 题逐层打分。

## 7. 目录划分的依据

```
sqlagent/
├── 内核（不依赖任何一条路）   config / db / guard / llm / schemas / prompts / tools
├── 路线 A                     workflow/graph.py       （LangGraph 显式图）
├── 路线 B                     agents/sql_agent.py     （create_agent）
├── 对接层                     chatbi.py / cli.py      （三道闸门、多轮、渲染、入口）
└── 评测层                     judge/ + evalset.py     （与生产路径解耦）
```

一条硬规则：**箭头只能从外往里指**。
`workflow/` 与 `agents/` 都依赖内核；内核**不反向依赖**任一路线；
`judge/` 只读被测路径的 trace，不侵入生产代码。这样任一路线可单独替换、单独评测。
