# 外部数据库接入指南

> 面向本项目 SQL Agent（`sql-agent-workflow.ipynb`）。
> 目标：把数据源从内置的 SQLite 示例库，平滑迁移到**外部真实业务库**
> （MySQL / PostgreSQL / SQL Server …），并保持「只读安全 + 流水线可控」不变。

本指南是 README「数据来源与外部数据库接入」一节的可执行展开版：
分阶段路线、方言对照、建只读账号、换库后的冒烟自检。

---

## 0. 现状速览

- **数据源**：同目录 SQLite 文件 `chinook.db`（约 884 KB，Chinook 示例库，真实文件非生成）。
- **链路**：LLM 吐文本 SQL → `is_readonly()` 守卫 → `check_sql()` 试跑 →
  `execute_sql()` → SQLAlchemy → sqlite3 → 读文件。**模型全程不碰数据库。**
- **唯一真正需要改的入口**：连接串 `DB_URL`。反射层（`create_engine` / `inspect`）
  与流水线编排（`run_workflow` / `ChatBI`）**跨库通用**。

## 1. 接入点清单（改哪里）

| 要改的东西 | 位置 | 现状 | 换库时怎么做 |
|---|---|---|---|
| 库文件定位 | 环境准备 cell | `find_up("chinook.db")` 硬编码文件名 | 改文件名，或改成分支逻辑 |
| 连接串 | 环境准备 cell | `DB_URL = f"sqlite:///{_db_path}"` | **换成目标库 URL（关键）** |
| 驱动 | `pip` 依赖 | sqlite 内置，无需安装 | 外部库需 `pip install` 驱动 |
| 反射 / 建连 | `DBParser.__init__` | `create_engine(db_url)` / `inspect(...)` | **不用改** |
| 只读守卫 | `is_readonly()` | 关键字白名单 | 方言相关，需回归复核 |
| 试跑 | `check_sql()` | `engine.begin()`（自动提交） | 方言相关；建议改只读事务 |

## 2. 分阶段路线（Gate 0 → 5）

原则：**先跑通，再优化**。每一步都可独立验收，不一次到位。

### Gate 0 · 现状
SQLite 本地文件，零配置。作为基线。

### Gate 1 · 换个 SQLite 文件（先验证「换源」这件事本身）
1. 把目标 `.db` 放到 notebook **同目录**（`find_up` 从 CWD 逐级向上找）。
2. 改环境准备 cell 里的文件名：`find_up("你的库.db")`。

- 不涉驱动 / 网络 / 凭据，成本最低，用来确认「换源 = 改一行」。
- **验收**：能反射出新库的表、整条流水线跑通一条聚合查询。

### Gate 2 · 接入外部库（务必用只读账号）
1. 装驱动：

   ```bash
   pip install pymysql            # MySQL / MariaDB
   pip install "psycopg[binary]"  # PostgreSQL
   pip install pyodbc             # SQL Server
   ```

2. 在数据库侧建**只读账号**（第一道护栏，独立于代码）：

   ```sql
   -- MySQL
   CREATE USER 'ro_user'@'%' IDENTIFIED BY '<password>';
   GRANT SELECT ON chinook.* TO 'ro_user'@'%';
   FLUSH PRIVILEGES;
   ```

   ```sql
   -- PostgreSQL
   CREATE ROLE ro_user LOGIN PASSWORD '<password>';
   GRANT CONNECT ON DATABASE <db> TO ro_user;
   GRANT USAGE ON SCHEMA public TO ro_user;
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO ro_user;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO ro_user;
   ```

3. 凭据进项目根 `.env`（沿用脱敏机制，`.gitignore` 排除 `.env`）：

   ```
   DB_URL=mysql+pymysql://ro_user:<password>@<host>:3306/chinook?charset=utf8mb4
   ```

4. 代码改成分支读取（外部库优先，退回内置 SQLite）：

   ```python
   import os
   DB_URL = os.environ.get("DB_URL") or f"sqlite:///{_db_path}"
   ```

- **风险**：网络可达性、连接超时、**连接串泄漏（绝不能打印 / 写进 notebook 输出）**。
- **验收**：`DBParser` 能反射外部库；一条聚合查询返回正确结果。

### Gate 3 · 适配方言与守卫
- **生成提示词**：从「你是 SQLite 专家」改成目标方言，明确日期函数、`LIMIT`、
  字符串拼接（`||` vs `CONCAT`）、标识符引号等差异。
- **只读守卫**：`is_readonly()` 的「首词必须 SELECT/WITH + 禁写关键字 + 禁多语句」
  跨库基本通用，但**必须回归复核**（如 `SHOW` / `EXPLAIN` / `CALL` 等方言关键字）。
- **试跑**：`check_sql()` 现在用 `engine.begin()`（会自动提交）；对只读 SELECT 无害，
  但建议改为只读事务（`BEGIN` + `ROLLBACK`），或直接靠 Gate 2 的只读账号兜底。
- **验收**：把 README 里的 `GOLDEN_SET` 思路搬过来，在目标库上跑一遍小评测集通过。

### Gate 4 · 大库可扩展性（从 demo 到真实库必须跨的坎）
- **问题**：`DBParser` 初始化会**逐表逐字段跑统计**（distinct / 众数 / max / min / 随机样例）。
  小库无感，但几百张表 / 上万字段的真实库会变成「初始化查询风暴」，拖死启动。
- **改法**：
  1. 统计改**惰性** —— 只对**被选中的表**计算，而非全库预计算；
  2. schema 上下文改**按问题检索候选表**（先给 LLM 表清单摘要 → 缩小范围 → 再取字段），
     而不是一次把所有表结构灌进提示词。
- **验收**：在大库上启动时间可接受，提示词长度受控。

### Gate 5 · 产品化
- 连接池参数（`pool_size` / `pool_pre_ping` / `max_overflow`）、查询超时与重试；
- **审计日志**：谁在何时跑了哪条 SQL、耗时多少（只读库尤其需要）；
- 凭据轮换 / 密钥管理（不要长期用静态口令）；
- 把「只读强约束」落到 CI / 演练里，确认写操作真的进不来。

## 3. 方言对照表（生成 SQL 时最常踩的坑）

| 维度 | SQLite | MySQL | PostgreSQL |
|---|---|---|---|
| SQLAlchemy URL | `sqlite:///file.db` | `mysql+pymysql://…` | `postgresql+psycopg://…` |
| 字符串拼接 | `\|\|` | `CONCAT(a, b)` | `\|\|` |
| 限制行数 | `LIMIT n` | `LIMIT n` | `LIMIT n` |
| 日期函数 | `date()` / `strftime()` | `DATE_FORMAT()` | `to_char()` |
| 标识符大小写 | 不敏感（默认） | 视 collation | 折叠为小写（加引号才区分） |
| 取当前时间 | `datetime('now')` | `NOW()` | `NOW()` / `CURRENT_TIMESTAMP` |
| 只读手段 | 文件系统只读 | `GRANT SELECT` | 只读 role |

## 4. 换库后的冒烟自检

改完 `DB_URL` 后，先跑这段确认「连得上 + 反射正常 + 查询能跑」：

```python
from sqlalchemy import create_engine, inspect, text

engine = create_engine(DB_URL)                    # DB_URL 来自 .env
insp = inspect(engine)
print("dialect :", engine.dialect.name)           # mysql / postgresql ...
print("tables  :", insp.get_table_names()[:10])

with engine.connect() as conn:
    print("smoke   :", conn.execute(text("SELECT 1")).fetchone())
```

- 通过后，再把 `DBParser` 指向它，跑一条业务聚合（如按国家统计发票数）与预期核对。

## 5. 常见坑

- **内部表混入**：`inspector.get_table_names()` 会带出 `sqlite_sequence` /
  `sqlite_stat1`（SQLite）或系统库表（PG/MySQL）。喂给 LLM 前要过滤。
- **自动提交**：`engine.begin()` 会提交；试跑 SQL 时优先用只读事务或只读账号。
- **连接串泄漏**：不要把 `DB_URL`（含口令）打印到 notebook 输出或日志里。
- **字符集 / 时区**：MySQL 建议 `charset=utf8mb4`；跨时区注意时间列语义。
- **大表 `COUNT(*)` 慢**：真实库上统计类查询可能很贵，配合 Gate 4 的惰性统计与超时限制。
- **表名大小写**：跨库搬迁 SQL 时，标识符大小写行为差异会导致「本地能跑、线上报错」。

## 6. 三条红线

1. **凭据绝不进代码 / notebook** —— 一律 `.env` + `.gitignore`。
2. **只读双保险** —— 代码守卫（`is_readonly`）+ 数据库只读账号，两者独立，
   任一失效还有另一道。
3. **大库别全量灌 schema** —— 否则提示词超长、token 爆炸、初始化拖死。
